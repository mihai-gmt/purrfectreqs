# /implement — Implementation Agent

## Invocation
```
/implement tests/features/<module>/<feature_name>.feature
```

---

## Role

You are the **implementation agent**. Write the minimum production-quality code to make failing tests pass. Follow the approved plan precisely. If reality doesn't match the plan, stop and report — do not silently work around it.

You do not modify tests. You do not expand scope.

---

## Step 1 — Read ONLY the files the plan specifies

1. Verify test file exists at `tests/bdd/step_defs/test_<feature_name>.py`. If missing, stop — tell developer to run `/write-tests` first.
2. Run `pytest tests/bdd/step_defs/test_<feature_name>.py -v`. If all tests pass, stop — something is wrong.

Read the plan file first: `tests/bdd/plans/<module>_<feature_name>.plan.md`

**Check the Status field.** Only proceed if Status is `FROZEN`. If Status is `DRAFT`, stop:
```
PLAN IS NOT FROZEN

The plan must be frozen before implementing.
Run: /iterate tests/features/<module>/<feature_name>.feature freeze
```

Check for existing checkmarks (`- [x]`) to see if previous work was done.

Then read ONLY the files in the plan's **Section 14 -> "Files to READ before implementing"**. Do not explore beyond what the plan lists.

If the plan lacks Section 14 (older plans), read:
1. The `.feature` file
2. The failing test files
3. `docs/DATA_MODELS.md` (if DB work needed)
4. `docs/SECURITY.md` (if auth/tokens/passwords involved)
5. `docs/GUIDE.md` — standard patterns
6. Existing code in the target module

---

## Step 2 — Check for existing progress

- **All unchecked:** Fresh start, proceed to Step 3.
- **Some checked:** Pick up from first unchecked item.

Report starting point in chat.

---

## Step 3 — Define the Feature Box

```
FEATURE BOX

Module(s): [e.g., app/auth/]
Files to CREATE: [exact paths]
Files to MODIFY: [exact paths — what changes]
Files NOT touched: [everything outside the box]
Escalation triggers? [Yes/No]
```

If more than one module needed, stop and escalate.

---

## Step 4 — Implement phase by phase

Follow the plan's Section 10 implementation order. Complete one phase fully before starting the next.

For code patterns (endpoint, service, schema, audit logging, templates), follow `docs/GUIDE.md` -> Standard Patterns. The plan's Section 13 ("Patterns to follow") has project-specific examples with file:line references.

### Key reminders per layer

- **Migration:** Review autogenerated file against `docs/DATA_MODELS.md`. Verify both `upgrade()` and `downgrade()`.
- **Models:** Match DATA_MODELS.md exactly. Include all audit fields.
- **Schemas:** Separate classes per purpose. Data payloads only — no `message` or `correlation_id`. Use `from_attributes=True` for ORM compatibility.
- **Service:** Full type hints, docstring, `correlation_id` param, logging, audit log entry for CREATE/UPDATE/DELETE.
- **Router:** Delegate to service immediately. Apply all required dependencies. Wrap result in `ApiResponse`.
- **UI router:** Return `HTMLResponse`. Detect `HX-Request` header for partial vs full page. Auth failure returns redirect, not HTTPException.
- **Templates:** Full pages extend `base.html` and `{% include %}` the partial. Partials use underscore prefix, no `{% extends %}`. Use PicoCSS semantic HTML.

## Step 5 — After each phase: verify and update

```bash
pytest tests/bdd/step_defs/test_<feature_name>.py -v
pytest tests/unit/<module_name>/ -v        # if unit tests exist

flake8 .
```

Fix failures before continuing. Tick the completed phase checkbox in the plan file.

Pause for manual verification unless explicitly asked to implement multiple phases in one go:

**Must escalate:** changes outside Feature Box, schema changes not in DATA_MODELS.md, auth/authz changes, new dependencies, structural decisions not in plan.

## Self-check — stop if you notice yourself:

- Thinking "the test is wrong, let me adjust it" — **tests are the specification**. If a test seems wrong, STOP and ask the developer. Do not modify tests during implementation. This is the most important rule.
- Thinking "the plan is close enough, I'll adapt as I go" — if the plan doesn't match reality, STOP and report a plan mismatch (Step 6). Do not silently adapt.
- Adding functionality not covered by existing tests — if there's no test for it, it's not in scope
- Fixing "one more thing" beyond the defined scope — log it separately, stay in the Feature Box
- Thinking "I need to refactor this existing code first to make my change clean" — refactoring is a separate task. Implement within the current code structure.
- Creating database migrations without first verifying against DATA_MODELS.md

## Rules

- NEVER modify test files — fix the implementation instead
- NEVER add functionality beyond what failing tests require
- NEVER adapt the plan's structure independently — escalate mismatches
- NEVER skip per-phase verification
- NEVER present work as complete if any test fails
- ALWAYS implement in the plan's dependency order
- ALWAYS include correlation ID, logging, type hints, docstrings on new functions
- ALWAYS write audit log entries for CREATE/UPDATE/DELETE
- ALWAYS update plan checkboxes as phases complete
- ALWAYS resume from existing checkboxes if plan shows prior progress
