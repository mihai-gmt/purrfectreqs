# ADR-0020: Full version pinning — top-level, transitive, models, and images

## Context

A TECH_STACK.md review (2026-04-21) surfaced three quiet supply-chain holes:
unpinned top-level dependencies in `pyproject.toml`, a `requirements.txt`
generated by `pip freeze` on the wrong platform (carrying ~18 dead CUDA
wheels), and an unpinned spaCy model download. The developer's own
course-correction triggered the fix: "I may have made an incorrect decision
when I said to go with unpinned dependencies."

## Decision

Everything is pinned: top-level dependencies in `pyproject.toml` with `==`;
`requirements.txt` as a full transitive lock; Docker image tags explicit
(never `latest`); static assets and ML/NLP models pinned by version and
checksum or vendored. Agents never change any version unless the task is
explicitly a dependency update. Future hardening (pip-tools regeneration,
`--require-hashes`) is documented but deferred — introducing it is an
escalation trigger.

## Rationale

"A pinned requirements.txt means every environment installs the same bytes
until the developer deliberately updates" (`docs/TECH_STACK.md`). A malicious
upstream release cannot ride in on a rebuild. The journal adds the second
lesson: lock files are authoritative only for the platform that generated
them — "question the inheritance."

## Consequences

### Positive

- Reproducible builds; a closed supply-chain surface; version drift between
  `pyproject.toml` and `requirements.txt` becomes detectable (`pip check`).

### Negative

- Security updates require deliberate bumps (mitigated by weekly pip-audit
  CI); two files must be kept in sync until pip-tools is adopted.

## Alternatives considered

### unpinned-top-level

The original state — ranges/bare names at top level, pins only in the freeze
file. Rejected after the review: it delegates the actual version choice to
whenever pip happens to re-resolve, which is precisely the supply-chain
window pinning closes.
