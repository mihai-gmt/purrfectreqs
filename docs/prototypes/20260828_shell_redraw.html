The shell after seven decisions

The first prototype's central mechanism — a sliding two-column window over a tree of any depth — no longer has anything to slide through. This redraw shows what replaced it: a standing two-section rail, a two-level outline you re-pivot instead of descend, and the requirement rendered as a document. Every state below is clickable.

Reading the shell

The rail

Two sections, not one list. Projects and Admin are global and always stand. The five project-scoped modules appear under a heading that names the active project — which also answers "where am I" without spending a breadcrumb on it. With no project open the second section is absent, not greyed out.

The outline

Two levels: group, then requirement. There is no third level to descend into, so there is no window to slide. Change the Group by control and the same eight requirements re-pivot under different headings. Source is the default axis; a requirement someone typed by hand falls under Added by hand.

The detail pane

The requirement as a document. Criteria in plain language, each expanding to its Gherkin scenarios. This is where the requirement → criterion → scenario chain is drawn — never in the outline, which would duplicate it and desynchronise on every edit.

The inspector

One pane, several jobs. AI proposals, analysis, validation results and traceability all arrive here on demand. What the first prototype called the "AI drawer" is this pane, not a fourth zone. It never opens beside the Focus Editor.

The Focus Editor

Its own route, so the back button is cancel. The rail and the outline yield to a read-only context strip carrying the breadcrumb and the parent criterion — the thing the author is formalising. Short edits never come here.

Intake

The funnel, in its own module. A pasted note and a parsed document both land as raw inputs. The AI decomposes; candidates wait. Accept writes the requirement and records where it came from. Dismiss soft-deletes it and keeps it in the audit trail.

Still open — decide these before anyone builds it

Does the Focus Editor keep the rail?

The ADR-0046 draft says the rail and the outline "yield to a context strip", and this prototype draws it that way — no rail. But the archetype table also says the shell is present. Either the strip replaces the rail, or a slim icon rail survives beside it. The drawing above is a choice, not a settled rule.

Where does the group-by axis live?

It is drawn as a control in the outline header. It could equally be a per-project saved preference. A saved preference needs somewhere to store it, which is a new mechanism for a small gain.

What does the outline do at 400 requirements?

The outline never paginates, by decision. Groups load their requirements on expand, so the cost is bounded per group — but a project whose default axis produces one group of 400 has no bound. Search may be the answer rather than a page control.

Does accepting a candidate open the new requirement?

Accepting in Intake creates a requirement in another module. Jumping the user there interrupts a review they are part-way through; staying put hides the result of their click. The prototype stays put and marks the candidate accepted.

What this is not: a visual design. Spacing, colour and type here are placeholders. The real thing inherits PicoCSS plus the token layer per FRONTEND.md §5. This artifact demonstrates geometry, state and information architecture only.

Implementation mapping. The rail is a Jinja partial re-rendered on project change. A group expands with hx-get /projects/{id}/requirements?group=… targeting the group body. The detail pane is a boosted navigation. The inspector is an hx-get swap. Accepting a scenario is hx-post /criteria/{id}/scenarios; accepting a candidate is hx-post /intake/candidates/{id}/accept. The Focus Editor is its own route with the Ace island — useStrictCSP set before the first ace.edit, or it renders wrong and nothing throws.

No inline handlers. Every control on this page is wired with addEventListener, the same discipline the strict CSP forces on the real app — the first prototype used onclick, which was logged as UI-13.
